# XRobot

XRobot resolves reusable C++ Modules to exact commits and generates a static C++
application entry for [LibXR](https://github.com/xrobot-org/libxr) BSPs. It is not a
build system: after `xrobot setup`, build with the BSP's own CMake, presets, Docker
or vendor commands. LibXR is usable without XRobot.

Documentation: <https://xrobot.work/docs/proj_man>. Governance: [GOVERNANCE.md](GOVERNANCE.md).
Releases: [RELEASE.md](RELEASE.md).

## Install

```sh
pip install xrobot==1.0.0
```

A BSP pins the tool version in `Modules/modules.yaml` (`xrobot: 1.0.0`); install
that version. `xrobot` warns when the installed version differs from the pin.
STM32 BSPs also use the CodeGenerator (`pip install libxr==6.0.0`), pinned by
`generator:` in `User/libxr_config.yaml`.

## BSP layout

The BSP root is the nearest directory containing `Modules/modules.yaml`; every
command works from any subdirectory, or with `-C DIR`.

| File | Committed | Meaning |
| --- | --- | --- |
| `Modules/modules.yaml` | yes | Requested Modules (`owner/Repo@ref`) and the `xrobot:` tool pin |
| `Modules/sources.yaml` | yes | Module catalogs (`index.yaml` URLs) and their priorities |
| `xrobot.lock` | yes | Exact commit of every Module in the dependency closure |
| `User/*.yaml` | yes | Application configurations (products); `User/libxr_config.yaml` is not one |
| Entry source under `User/` | yes | Registers BSP objects with `XR_REGISTER` and calls `XROBOT_MAIN()` |
| `Modules/<owner>/<Repo>/` | no | Module checkouts at the locked commits |
| `Modules/CMakeLists.txt` | no | Generated by `xrobot setup` |
| `User/xrobot_main.hpp` | no | Generated entry for the selected product |

`xrobot init` creates `Modules/modules.yaml`, `Modules/sources.yaml`,
`User/xrobot.yaml` and the `.gitignore` entries for the generated files.

## Quick start

```sh
xrobot init
xrobot module add xrobot-org/BlinkLED@dev
xrobot setup                              # fetch, lock, check configs, generate
xrobot instance add xrobot-org/BlinkLED   # adds instance blinkled_0
```

`instance add` writes every constructor parameter with its source default; a
dependency without a default is left empty (`null`, "not filled in"). Fill it with
the name of a registered BSP object:

```yaml
modules:
  - module: xrobot-org/BlinkLED
    id: blinkled_0
    args:
      - led: LED_R
      - blink_cycle: '250'
settings:
  monitor_sleep_ms: 1000
```

The entry source registers the objects that configurations may use and enters the
application:

```cpp
#include "xrobot_main.hpp"

// ... construct LED_R and the other BSP objects ...
XR_REGISTER(LED_R, LibXR::GPIO);
XROBOT_MAIN();
```

Then generate and build natively:

```sh
xrobot gen
cmake -S . -B build
cmake --build build
```

The BSP's CMake sets `XROBOT_MODULES_DIR` to `<BSP>/Modules` before adding LibXR.
LibXR then includes `Modules/CMakeLists.txt`, prints the selected product, and
fails the build when `User/xrobot_main.hpp` is missing or older than any input it
lists, naming the `xrobot gen -c <config>` command to run.

## Modules and the lock

`Modules/modules.yaml` lists the direct requests; dependencies come from each
Module's manifest:

```yaml
xrobot: 1.0.0
modules:
  - xrobot-org/BlinkLED@dev
  - QDU-Robomaster/Gimbal@same-or-dev
  - id: QDU-Robomaster/Chassis
    ref: 0123456789abcdef0123456789abcdef01234567
    context_ref: refs/heads/feature/new-api
```

A ref is a branch, a tag, a commit, or omitted (the remote default branch).
`refs/heads/...` / `refs/tags/...` disambiguate a name that is both.
`same-or-dev` uses the Module branch named like the BSP's current branch, otherwise
`dev`; on a BSP tag it requires the identical tag. `same` requires the matching
branch or tag. A detached checkout (CI) passes the logical BSP ref with
`--context-ref refs/heads/<branch>`; `context_ref` in a request does the same for
that Module and its dependencies.

`xrobot setup` resolves the requests into `xrobot.lock` and checks every Module out
at its locked commit (detached). The lock is authoritative afterwards:

| Command | Effect |
| --- | --- |
| `xrobot setup` | Keeps locked commits; added, removed or changed requests change only those entries |
| `xrobot setup --update MODULE...` | Re-resolves the named Modules |
| `xrobot setup --update` | Re-resolves every Module |
| `xrobot setup --frozen` | Restores exactly the lock; fails if `modules.yaml` changed |
| `xrobot setup --offline` | Uses only local checkouts and commits |
| `xrobot setup --release-ref REF` | Refuses commits that are not released for the target line |

`--update` also runs `xrobot sync` on every configuration. Setup never discards
local work: a Module with uncommitted changes, or at a local commit that is on no
remote branch or tag, stops it with an explanation. While developing a Module
inside a BSP, keep the changes uncommitted; push them to a branch of the Module and
run `xrobot setup --update <Module>` when they are ready.

Release gate: with `--release-ref refs/heads/dev` every locked commit must be on the
Module's `dev`; with `refs/heads/master`, `refs/heads/main` or a tag it must be on
the Module's `master` (or `main`). Explicitly requested tags pass. The same rule
applies to the `xrobot:` and `generator:` tool pins when they are commits; release
versions pass.

## Application configurations

Every `User/*.yaml` except `User/libxr_config.yaml` is an application
configuration; `xrobot setup` checks all of them. `xrobot gen -c <config>` selects a
product and writes `User/xrobot_main.hpp`, whose first lines name the config and
every file it read. `xrobot gen` and `xrobot setup` keep the current selection
(default `User/xrobot.yaml`).

```yaml
constexpr_namespace: BoardConfig        # default: ProjectConstexpr
constexprs:
  YawFeedbackId:
    type: uint16_t
    value: '522'
modules:
  - module: QDU-Robomaster/RMMotor
    id: motor_yaw
    args:
      - can_bus: can2
      - param:
          model: RMMotor::Model::MOTOR_GM6020
          reverse: 'false'
          feedback_id: BoardConfig::YawFeedbackId
settings:
  monitor_sleep_ms: 1000
```

- Instances are constructed and monitored in list order; `id` names the C++
  object. `args` names every parameter of one public constructor, in order.
  `template_args` lists template arguments as C++ text.
- Values are C++ text. `null`, `~` and an empty value mean "not filled in" and
  generation refuses them; write `nullptr` for a null pointer.
- A dependency parameter (reference or pointer without a default) takes a
  registered name, an earlier instance id, `&name`, or `nullptr` for a pointer. An
  optional dependency is a pointer parameter without a default.
- A struct or class defined in a Module header is written as a mapping that names
  all its fields (or one constructor's parameters) in declaration order.
  Positional lists and positional braces are rejected for such types.
  `xrobot sync` adds fields and parameters introduced by a new Module version with
  their defaults and drops removed ones. Other types take any C++ expression,
  including braces.
- `constexprs` become `inline constexpr` constants in `constexpr_namespace`;
  `constexpr_includes` adds headers their types need.
- YAML anchors, aliases and tags are rejected; share values through `constexprs`.
- Generated code carries `#line` directives, so compiler errors point to the YAML
  line.

Editing commands keep comments and write the canonical layout that
`xrobot format` enforces (`xrobot format --check` in CI):

```sh
xrobot instance add owner/Repo [--id ID]
xrobot instance set ID args.led '"LED_B"'   # PATH: id, template_args[n], args.<p>[.<field>|[n]]...; VALUE is JSON
xrobot instance rename ID NEW_ID            # also renames references in the same config
xrobot instance remove ID
xrobot sync
xrobot format
xrobot describe                             # BSP state as JSON, for editors
```

`xrobot instance` edits the selected product unless `-c CONFIG` is given.

## Entry source and registration

Exactly one source under `User/` calls `XROBOT_MAIN()`. Before the call it
registers BSP objects with `XR_REGISTER(name, Type)`, one type per name. To expose
an object as another type, declare a reference and register that name:

```cpp
LibXR::CAN& can1 = fdcan1;
XR_REGISTER(fdcan1, LibXR::FDCAN);
XR_REGISTER(can1, LibXR::CAN);
XROBOT_MAIN();
```

The generated `XRobotMain` takes the registered objects the selected product uses
as references and constructs the instances as function-local `static` objects.
It then loops: it calls each instance's public `void OnMonitor()` (where one
exists) in configuration order and sleeps `settings.monitor_sleep_ms`.
`XROBOT_MAIN()` does not return. There is no runtime container, registry or
manager; registered objects must outlive the application.

The CodeGenerator (`xr_gen_code_stm32 --xrobot`) writes the `XR_REGISTER` lines
and `XROBOT_MAIN();` into `User/app_main.cpp`.

## Writing a Module

A Module is a Git repository `owner/Repo` whose primary header `Repo.hpp` declares
a plain global C++ class `Repo`. Its public constructor is the interface:
dependencies (references or pointers without defaults) first, then value
configuration with defaults. Metadata stays in the header:

```cpp
/* === MODULE MANIFEST V2 ===
module_description: Motor controller
depends:
  - id: QDU-Robomaster/Motor
    ref: same-or-dev
=== END MANIFEST === */
```

The manifest holds only `module_description`, `depends` and `standalone`;
`standalone: false` marks a library that is not instantiated on its own.

```sh
xrobot new-module MySensor --desc "IMU driver" \
  --constructor "LibXR::I2C& i2c" --constructor "uint32_t period_ms = 10"
xrobot module show MySensor                 # manifest and constructors
```

Module CI calls the shared workflow
`xrobot-org/XRobot/.github/workflows/module-ci.yml`. It resolves the Module's
dependencies and compiles the Module sources plus one constructor call written by
`xrobot check-module` against LibXR on Linux; the call uses `void*` placeholders
for dependencies and is never executed. Inputs: `xrobot-ref`, `libxr-ref`,
`dependency-ref`, `template-args` (JSON list), `image`, `apt-packages`,
`cmake-options`, `ctest-regex`, `ctest-timeout` (seconds per test, default 15).

## Catalogs

`Modules/sources.yaml` lists catalogs; a smaller `priority` wins, and equal
priorities that disagree about a package are rejected. A catalog `index.yaml` lists
Module and BSP repositories:

```yaml
namespace: xrobot-org
modules:
  - https://github.com/xrobot-org/BlinkLED.git
bsps:
  - https://github.com/QDU-Robomaster/bsp-dev-c.git
```

A GitHub URL gives the identity `owner/Repo`. An entry may also be a mapping with
`id`, `repo` and `status` (`community`, `verified` or `official`; the latter two
need `tested_ref` and `tested_libxr`). `mirror_of` marks a mirror catalog: sources
are fetched from it while `xrobot.lock` keeps the canonical URL.

```sh
xrobot source list [--type module|bsp]
xrobot source search STM32
xrobot source get owner/Repo
xrobot source find owner/Repo
xrobot source add-source URL --priority 1
xrobot source create-index -o my-index.yaml --namespace my-team
xrobot source add-index https://github.com/my-team/MyModule.git --index my-index.yaml
```

`xrobot source` reads `Modules/sources.yaml` relative to the current directory;
pass `--sources PATH` before the subcommand otherwise.

## Commands

| Command | Purpose |
| --- | --- |
| `xrobot init` | Create the BSP files in the current directory |
| `xrobot setup` | Resolve and lock Modules, check every config, regenerate the entry |
| `xrobot gen [-c CONFIG]` | Generate `User/xrobot_main.hpp` (select a product) |
| `xrobot describe [-c CONFIG]` | Print the BSP state as JSON |
| `xrobot sync [-c CONFIG]...` | Add new fields/parameters with defaults, drop removed ones |
| `xrobot format [--check] [-c CONFIG]...` | Rewrite configs in the canonical layout |
| `xrobot instance [-c CONFIG] add\|set\|remove\|rename` | Edit one instance |
| `xrobot module add\|remove owner/Repo[@ref]` | Edit `Modules/modules.yaml` |
| `xrobot module show PATH` | Print a Module's manifest and constructors |
| `xrobot new-module NAME` | Create a Module skeleton with CMake, README and CI |
| `xrobot check-module MODULE` | Write the never-executed constructor call used by Module CI |
| `xrobot source ...` | Query or edit catalogs |

## Tests

```sh
python -m unittest discover -s tests -v
```

C++ test cases use `CXX` (default `g++`); without a compiler they are reported as
skipped.
